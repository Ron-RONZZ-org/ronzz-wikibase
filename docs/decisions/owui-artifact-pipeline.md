# Decision: AI-generated graphics → wiki (Open WebUI artifact pipeline)

- **Status**: Accepted (Oct 14 2026) — implemented + deployed
- **Scope**: `llm.ronzz.org` (Open WebUI) code interpreter → `wikibase.ronzz.org` File namespace, through the wiki-writer MCP
- **Decider**: Rongzhou (`ron@ronzz.org`)

## Context

The OWUI agent (Veramiko) runs Python in the code interpreter (Pyodide, browser-side). A user
asking for a chart or diagram should be able to (a) see and download it, and (b) upload it to the
wiki — but the pieces did not connect:

- Pyodide runs in the browser; the generated bytes live in the browser, not on the server.
- `execute_code` (backend) persists **only** `data:image/png;base64` output: it uploads it to the
  OWUI files store and rewrites the line to `![Output Image](/api/v1/files/<id>/content)`
  **before** the model sees it. So for PNG the model gets a file id/URL but never the bytes.
- The `<code_interpreter>` tag path already accepted any `data:image/\w+;base64`; the
  `execute_code` tool path lagged with a literal `data:image/png;base64` check. And the shared
  `BASE64_IMAGE_URL_PREFIX = data:image/\w+;base64,` cannot match `svg+xml` (the `+`), so SVG
  failed on **every** path.
- `upload-file` reads only from an allowlisted dir inside the writer container;
  `upload-file-from-url` is SSRF-guarded (public URLs only); `/api/v1/files/<id>/content` is
  auth-gated.

Inspect/download was already native (Pyodide file browser + inline render), so only the
generation → wiki bridge was missing.

## Decision

1. **Patch Open WebUI** (fork) rather than add a separate "duplicate" service — the base64 never
   leaves OWUI, so the format extension must happen where the base64 exists.
   - **A (upstreamable)**: widen the shared prefix to `[\w.+-]+` and route every code-execution
     site through it (`tools/builtin.py` ×2, `utils/middleware.py` ×3, `utils/files.py`).
   - **B (ours)**: `execute_code` returns a `files` array (`id`/`url`/`name`/`path`).
2. **Fork** `open-webui/open-webui` → `Ron-RONZZ-org/open-webui`, branch `ronzz/artifact-pipeline`
   off tag `v0.12.0` (tag `ronzz-v0.12.0`). Build a **derived** arm64 image (`Dockerfile.ronzz`:
   the pinned upstream image + the patched modules) through the fork's CI, published to
   `ghcr.io/ron-ronzz-org/open-webui:ronzz-v0.12.0` and pinned by digest.
3. **Bridge through the existing writer** — no new MCP server: `mediawiki-mcp-writer` gets the
   OWUI `uploads` subpath mounted **read-only** (`volume.subpath: uploads`, so `webui.db` is not
   shared) and lists it in `uploadDirs`. The model passes `files[].path` to `upload-file`.
4. **Test through the public suite** — fork `open-webui/tests`; add `open-webui-repository`,
   `tests-repository` and `fast` inputs (backwards-compatible) and a test driving both the tag
   path and the tool path through the fake-Jupyter harness.

## Consequences

- Every base64 image format the code interpreter prints (PNG, JPEG, GIF, WEBP, SVG) is uploaded
  and served from the files API.
- The user keeps native inspect/download (inline render + Pyodide file browser).
- Cost: a standing rebase on the two upstreams (the diff is a few lines) and coupling to OWUI
  internals (`{id}_{name}`, `generated-image.<ext>`, `/api/v1/files/<id>/content`).
- Upstream: Open WebUI does **not** accept unsolicited PRs; commit A is proposed as issue
  `open-webui/open-webui#32432`. When upstream lands it, drop it from the fork.
- Security: the writer can read the whole OWUI `uploads` dir (single-tenant, few editors); a
  stored SVG is served `Content-Disposition: attachment` (existing behaviour).
